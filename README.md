# DS-CNN Accelerator — Phase 1 Design Space Exploration

Starter kit for the model↔hardware co-design loop. Phase 1 lives entirely in
Python + Timeloop; no RTL yet. The goal of this phase is a **defensible design
point** and a **committed set of predictions** to test in Phase 3.

## What's here

```

│   └── baseline_8x8.yaml         # 8x8 weight-stationary array, the thing you edit

## Setup — use the Docker image, do not fight a native install

```bash
git clone --recurse-submodules \
  https://github.com/Accelergy-Project/accelergy-timeloop-infrastructure.git
cd accelergy-timeloop-infrastructure
make pull
# x86:
DOCKER_ARCH=amd64 docker-compose run infrastructure
# Apple silicon:
DOCKER_ARCH=arm64 docker-compose run infrastructure
```

Then, inside the container, from this project directory:

```bash
python3 scripts/make_problems.py   # 1. generate the layer problems
python3 scripts/sweep.py           # 2. run the sweep (minutes, parallelized)
python3 scripts/analyze.py         # 3. or paste into Jupyter cell-by-cell
```

## Do this FIRST, before your own workload

Reproduce a shipped baseline (the Eyeriss config in the exercises repo) and
confirm you get sane numbers. You want a known-good reference before you trust
any number this kit produces. One evening, saves days of confusion later.

## The three traps, written down so they don't surprise you

1. **Stats field names drift between releases.** `sweep.py` pulls energy /
   cycles / area / utilization defensively and will record `None` if it
   guessed wrong. On your **first successful run**, open
   `runs/<tag>/timeloop-mapper.stats.txt`, read the real field names, and fix
   the `g(stats, ...)` calls once. Everything downstream depends on this.

2. **45nm ≠ 130nm.** Accelergy's default tables are 45nm. If you tape out on
   Sky130 (130nm), absolute energy/area will not match — not close. This is
   fine for Phase 1 because DSE is about *relative* ranking between points.
   But write the note now; "I knew and accounted for it" is a far stronger
   Phase 3 story than finding out after synthesis.

3. **Depthwise needs a grouped-conv shape.** The projection in
   `make_problems.py` still technically lets every output channel see every
   input channel. For a *true* depthwise result, either model it as 64
   separate C=1,M=1 problems and sum, or add a group dimension. Start with the
   ugly-but-unambiguous version — the idle-array finding shows up either way.

## The one habit that makes Phase 3 work

`analyze.py` ends with a `PREDICTIONS` dict. Fill it in from your chosen design
point and **git-commit it, dated, before writing any RTL**. That single act
converts Phase 3 from "here's a story about why the numbers differ" into "here
was my prediction, here's the measurement, here's the gap and its cause."
That gap is the entire co-design pitch. Don't skip it.
```
git add scripts/analyze.py
git commit -m "Phase 1 predictions locked: 8x8 glb2048, E=X uJ, A=Y um2 (pre-RTL)"
```

## When Phase 1 is done

You should be able to say, in two sentences to an interviewer:
*"I swept N design points across the three DS-CNN layer types and found a
{array} array with a {size} buffer was Pareto-optimal, driven mostly by
{buffer energy / utilization}. Depthwise layers capped utilization at {X}%,
which is why a bigger array lost — and I predicted {E} µJ per inference before
building the RTL to check it."*

If you can say that, you're already past most applicants for these roles.
